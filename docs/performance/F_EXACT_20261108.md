# F-EXACT — construcción paralela exacta de pelo largo

## Estado y alcance

El commit inicial `dbd060309129da3d63fb1a8f46b20309415ba276` fue revisado por el coordinador,
pero **no fue aceptado**. Los gates adicionales de este informe se ejecutaron después; esta
actualización no declara aceptación visual/GPU, que continúa bajo responsabilidad del coordinador.

El camino paralelo quedó opt-in y desactivado por defecto. `LongHairSet_Build` conserva el
constructor serial y los callbacks legacy; `LongHairSet_BuildParallel` exige callback/contexto
inmutable y thread-safe, usa un scheduler privado persistente, y conserva publicación
transaccional. La selección de `MONSTER_LONG_HAIR_THREADS` es por runtime: `1` fuerza serial,
2/4/8 habilitan sólo el pool retenido con ese tamaño y un cambio incompatible cae a serial.
No se cambia el entorno global ni se programa trabajo gráfico desde workers.

Las raíces permanecen seriales; colisión/certificación y folículos se dividen por guía con una
barrera completa entre fases. Se mantienen el orden aritmético local, auditoría de 72 muestras,
umbral `.0005*scale`, filtros/reintentos, descriptores, identidades, campo combinado exacto
`min(body, jaw snapshot)` y las 80 filas GPU por guía. El scheduler y el contexto jaw se conservan
hasta el join; el camino sin perfilado no lee el reloj ni actualiza contadores.

## Gates adicionales y recuperación del runaway

### Causa raíz y limpieza de procesos

Un primer intento del caso bounded ASan quedó ejecutándose porque el bucle del harness avanzaba
con `threads = threads == 1 ? 4 : 8`; después de 8 volvía a 8 para siempre. El proceso no mostró
una recursión ni un deadlock de C: el defecto fue el límite del bucle en el test driver. Ese intento
fue **interrumpido y no cuenta como PASS**. Se cambió a la secuencia explícita `{1,4,8}`; se confirmó
que el PID comunicado por el coordinador ya no existía y no se encontró proceso huérfano.

Ambos helpers de validación (oráculo/sanitizadores y benchmark) ahora lanzan cada job en un grupo
de procesos aislado, con deadline interno, terminación SIGTERM/SIGKILL y `wait()` del líder. Sus
handlers de SIGTERM/SIGINT/SIGHUP limpian el grupo antes de salir; en Linux el hijo directo usa
`PR_SET_PDEATHSIG` para cubrir la muerte inesperada del padre. Las pruebas crean un hijo y un nieto
falsos, fuerzan timeout o SIGTERM al padre y comprueban que ambos PID desaparezcan. El TSan host
mapping retry usa `setarch x86_64 -R` dentro del mismo límite.
